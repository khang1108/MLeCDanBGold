# HCMAI Agentic Coding Guide

This file is the **repository-level orientation and coding guardrail** for agents working on the **HCMAI / Ho Chi Minh City AI Challenge 2026 multimodal video retrieval project**.

It is intentionally **not** a sprint plan, task list, implementation checklist, or temporary migration document. It should remain useful across many iterations of the project.

When this file conflicts with the user's latest explicit instruction or an official competition rule, the newer authoritative instruction wins.

---

## 1. Project Overview

HCMAI is a hackathon and applied-research system for multimodal video retrieval and reasoning.

The system searches long videos from natural-language queries using evidence such as:

- visual keyframes;
- generated captions;
- OCR;
- detected objects;
- ASR / transcripts;
- temporal relationships;
- VLM / LLM reasoning when necessary.

The repository targets three major competition task families:

- **KIS** — find the described video/event and return a valid competition frame;
- **VQA / Q&A** — localize the relevant event and answer a grounded question;
- **TRAKE** — retrieve a video and align an ordered sequence of semantic events.

The important reasoning unit is not always one isolated frame. Evidence may be distributed across several nearby keyframes or moments in the same temporal event.

---

## 2. Project Goal and Mental Model

The project aims to reliably retrieve the **right temporal evidence** and then produce the correct task-specific output.

Preferred mental model:

```text
query
  -> multimodal retrieval
  -> structured evidence
  -> temporal localization / alignment
  -> task-specific reasoning
  -> competition-compatible output
```

Keep task-specific heads thin when logic can be shared cleanly, but do not force different task semantics into one over-generalized abstraction.

---

## 3. Current Data Direction

For the HCMAI 2026 competition profile:

- BTC-provided **Keyframes** are canonical visual inputs;
- BTC-provided **Objects** are imported, not re-detected;
- Caption, OCR, and ASR are generated by this project;
- custom video preprocessing/keyframe extraction is not required in the active competition preparation path.

Current enrichment direction:

```text
BTC Keyframes
  -> Caption
  -> OCR
  -> Visual representation

BTC Objects
  -> Object normalization

Videos
  -> timestamped ASR

Caption + normalized OCR + normalized Objects
  -> deterministic FrameContext
```

Rules:

- specialist evidence remains available independently;
- a fused/context representation is an additional view, not a replacement;
- ASR is timeline evidence, not inherently frame-native;
- expensive enrichment/index creation is offline;
- online serving must not silently regenerate large artifacts.

Detailed implementation belongs in specs/plans, not in this file.

## 4. Repository Structure

The exact tree may evolve. Responsibilities matter more than filenames.

```text
src/hcmai/
├── api/             # HTTP transport
├── common/          # shared schemas/config/cross-cutting utilities
├── data/            # ingestion, enrichment, stores, canonical metadata
├── thundercompute/  # model gateways, inference adapters, and model config
├── orchestration/   # application workflow composition
├── pipelines/
│   ├── kis/         # KIS-specific logic
│   ├── vqa/         # VQA-specific logic
│   └── trake/       # TRAKE-specific logic
├── retrieval/       # embeddings, indexes, retrieval, fusion, reranking
└── ...

tests/               # tests and hand-checkable fixtures
configs/             # tunable configuration
docs/                # architecture/specs/plans
KNOWLEDGE.md          # persistent research knowledge
```

### Package ownership

**`common/`**
- authoritative shared contracts and configuration;
- only truly cross-cutting utilities;
- search for existing types before creating new ones.

**`data/`**
- canonical frame ingestion;
- Caption/OCR/Object/ASR artifacts;
- artifact lineage/versioning;
- data stores and lookup.

Do not put KIS/VQA/TRAKE reasoning here.

**`retrieval/`**
- embeddings and indexes;
- modality-specific retrieval;
- filtering/fusion/reranking;
- retrieval evaluation.

Preserve modality provenance and canonical identity.

**`pipelines/`**
- task-specific semantics after shared retrieval/data capabilities.

Do not duplicate generic retrieval/index code here.

**`orchestration/`**
- compose services and task workflows;
- do not duplicate low-level model adapters.

**`api/`**
- keep routers thin;
- parse/validate requests, call services, shape responses;
- no FAISS search, ranking, temporal alignment, or model inference in routes when a service already owns it.

## 5. Canonical Identity Rules

Canonical identity is correctness-critical.

Preserve at least:

```text
video_id
frame_id
frame_idx
timestamp_ms
```

### `frame_id`

`frame_id` is the **internal canonical identity** used for joins, stores, evidence, retrieval candidates, and internal references.

### `frame_idx`

`frame_idx` is the **competition-facing frame coordinate** used for submission.

Do not confuse it with:

- keyframe order;
- image filename number;
- decode position;
- timestamp;
- internal `frame_id`.

### `video_id`

`video_id` identifies the source video and must travel with frame evidence.

### Keyframe order

Keyframe order is only the position of a keyframe in the BTC keyframe set. It must never silently replace `frame_idx`.

### Identity invariants

Never allow:

- rerankers to rewrite identity;
- model providers to invent identity;
- array/index positions to become frame identity;
- deduplication to merge canonical frames without an explicit rule.

## 6. Evidence Rules

Evidence must remain structured and traceable.

Do not destructively flatten all modalities into one anonymous text blob and discard the originals.

Examples of specialist/derived contracts may include:

```text
CaptionEvidence
OCREvidence
ObjectEvidence
ASRSegment
FrameContext
```

A derived context representation is allowed, but source evidence must remain available for debugging, ablation, reranking, exact matching, and future research.

### Missing evidence is not negative evidence

Distinguish when relevant:

```text
not evaluated
no useful evidence found
evidence matched
```

Do not silently turn “not evaluated” into score `0` when that changes semantics.

### Object evidence

Do not deduplicate repeated labels if doing so loses counts.

```text
person
person
person
car
```

must not collapse to only:

```text
person
car
```

when multiplicity matters.

### OCR evidence

Keep raw OCR separately from normalized OCR.

Normalization may help retrieval but must not destroy original evidence.

### ASR evidence

Treat ASR as timestamped timeline evidence. Speech near a frame does not automatically describe that frame.

## 7. Hackathon / Research Engineering Philosophy

This is a **hackathon and applied-research codebase**, not an enterprise product.

Default priority:

```text
correct
-> understandable
-> easy to debug
-> easy to experiment with
-> measurable
-> fast enough
```

Do **not** optimize for maximum abstraction or production infrastructure by default.

### Keep implementations simple

Use the smallest implementation that correctly supports the current requirement or experiment.

Avoid unnecessary:

- dependency injection frameworks;
- abstract factories;
- service registries;
- generic plugin frameworks;
- base classes with only one implementation;
- speculative extensibility;
- distributed infrastructure for a local/offline problem;
- premature caching layers;
- complex concurrency when sequential code is sufficient;
- microservice boundaries inside a hackathon backend.

A simple function is often better than a hierarchy of abstractions.

### Optimize after measurement

Do not redesign because something merely “looks slow”. Measure the failing stage first.

Examples:

```text
image loading
embedding
FAISS retrieval
fusion
reranking
network transfer
VLM inference
```

No measurement means no verified bottleneck.

### Debuggability is a feature

Prefer code that is easy to inspect using:

- a debugger;
- clear logs;
- small fixtures;
- deterministic intermediate artifacts;
- simple reruns.

Do not make code clever at the cost of observability.

## 8. Code Style, Comments, and Docstrings

Agent-written code must be understandable by a teammate who did not write it.

### Module docstrings

Every non-trivial Python source file must have a module-level docstring describing:

- what the module owns;
- what it intentionally does not own when relevant;
- important invariants/boundaries.

Example:

```python
"""Build deterministic frame context from specialist evidence.

This module joins Caption, OCR, and Object evidence. It does not perform
model inference and does not include ASR in FrameContext V1.
"""
```

### Class docstrings

Every public class must have a useful docstring explaining its responsibility.

For domain contracts, explain non-obvious field semantics.

### Function/method docstrings

Every public function and method must have a useful docstring.

Private functions also need docstrings when intent, assumptions, or invariants are not obvious.

Bad:

```python
def build_context(...):
    """Build context."""
```

Better:

```python
def build_context(...):
    """Serialize usable Caption, OCR, and Object evidence into FrameContext.

    Missing modalities are omitted and no semantic rewriting is performed.
    """
```

### Comments explain WHY

Comments should explain:

- why code exists;
- what invariant it protects;
- why an approach was chosen;
- non-obvious competition semantics;
- temporary compatibility constraints;
- research assumptions still requiring validation.

Bad:

```python
# Increment index.
index += 1
```

Good:

```python
# Preserve the organizer-provided frame_idx because this is the coordinate
# used for submission. Keyframe order must not replace it.
frame_idx = row["frame_idx"]
```

Do not fill files with comments that merely translate Python into English.

### Whitespace and readability

Use blank lines between logical stages.

Prefer visually clear code:

```text
validate input

build evidence

persist artifact
```

instead of dense blocks mixing unrelated operations.

### Focused functions/files

Functions and files should have clear ownership.

Do not create a giant module containing unrelated logic, but also do not split trivial helpers into dozens of tiny files without a real boundary.

## 9. Reuse Before Creating Abstractions

Before introducing a new:

```text
schema
DTO
model
protocol
service
adapter
result wrapper
base class
factory
```

search the repository for overlapping semantics.

Prefer:

```text
reuse
-> extend
-> promote/generalize
-> replace
-> create new only when necessary
```

Avoid dead abstraction families such as:

```text
Candidate
CandidateV2
NewCandidate
TemporalCandidateV2
FinalCandidate
```

A new abstraction is justified only when:

1. no active type cleanly represents the semantics;
2. it has an immediate runtime/test consumer;
3. ownership is clear;
4. compatibility reasons are explicit if an older type remains.

## 10. Research-First Engineering

This repository is also an R&D project.

For non-trivial algorithmic decisions, use an available **scholarly research plugin/tool** before deciding on the implementation.

Research is especially expected for:

- multimodal retrieval;
- embedding strategy;
- multimodal fusion;
- temporal retrieval/alignment;
- reranking;
- query decomposition/planning;
- VQA evidence selection;
- model selection;
- scoring functions;
- learned weighting;
- performance/accuracy optimization hypotheses.

Prefer sources in roughly this order:

1. peer-reviewed conference/journal papers;
2. official author implementations;
3. strong technical reports/arXiv when peer-reviewed sources are unavailable;
4. official model/documentation sources.

Do not base major research decisions mainly on random blog posts when primary sources exist.

### Do not over-apply the research rule

Research is normally unnecessary for trivial changes such as:

- renaming a variable;
- formatting;
- typo fixes;
- obvious type annotations;
- moving a helper without semantic change;
- straightforward bugs with already verified root cause.

Use judgment.

### Papers inform hypotheses; they do not prove HCMAI improvements

Correct chain:

```text
paper / prior work
  -> HCMAI hypothesis
  -> controlled experiment
  -> measured result
  -> accept / reject / refine
```

Never claim “this improves accuracy” when the real status is only “this is expected to improve accuracy”.

## 11. `KNOWLEDGE.md` Research Memory

Material research findings must be saved in repository-local `KNOWLEDGE.md`.

`KNOWLEDGE.md` is the persistent R&D memory of the project so agents and teammates do not repeatedly rediscover the same papers, assumptions, failed ideas, and experiment motivations.

Update it when research leads to:

- an architecture decision;
- a retrieval/fusion idea;
- model-selection reasoning;
- a useful paper or official implementation;
- an experiment worth running;
- a rejected approach worth remembering;
- a research gap;
- a potentially publishable idea.

Do not use it as a dumping ground for routine code changes.

### Recommended entry format

```markdown
## Query-aware multimodal fusion

**Date:** YYYY-MM-DD
**Problem:** Static fusion may introduce noise from irrelevant modalities.

### Sources
- Paper / implementation / official source

### Findings
What the sources actually show.

### Relevance to HCMAI
Why the findings may or may not transfer.

### Status
PAPER-SUPPORTED / PROPOSED / VERIFIED / REJECTED

### Decision or Experiment
What we decided or how we will validate it.
```

### Claim labels

Use these labels when useful:

- **SOURCE** — verified from code/tests/config/artifacts/official rules/measured HCMAI experiment;
- **PAPER** — supported by literature or an official implementation;
- **PROPOSED** — engineering/research hypothesis requiring HCMAI validation;
- **VERIFIED** — confirmed by reproducible HCMAI experiment;
- **REJECTED** — intentionally not adopted after analysis/experiment.

## 12. Paper-Worthy Ideas Must Be Discussed

If an agent discovers a potentially meaningful research contribution, it must **not silently implement it as an ordinary refactor**.

Surface the idea to the user and explain:

1. the idea;
2. why it may be research-worthy;
3. related work;
4. what may actually be new;
5. how to validate it;
6. required ablations.

Potential signals include:

- a research gap;
- a novel combination of existing methods;
- an HCMAI-specific formulation that appears underexplored;
- a strong ablation opportunity;
- a potentially publishable retrieval/reasoning technique.

Do not oversell novelty. Search related work first and say when novelty is uncertain.

---

## 13. Experiment Discipline

Every non-trivial optimization should have a hypothesis and baseline.

Preferred pattern:

```text
problem
-> hypothesis
-> baseline
-> proposed change
-> metric
-> experiment
-> result
-> decision
```

Record enough information to reproduce important experiments:

- dataset/query-set version;
- model checkpoint;
- artifact/index version;
- config;
- relevant code revision;
- hardware/provider;
- metrics;
- latency;
- major failure cases.

Use ablations whenever practical.

Example:

```text
baseline
+ OCR hybrid retrieval
+ context retrieval
+ object retrieval
+ query-aware fusion
```

should not automatically be reported as one indivisible improvement.

Measure the metric that matches the failure mode.

- retrieval problem -> retrieval recall/ranking;
- localization problem -> scene/window/evidence recall;
- VQA reasoning problem -> oracle-localization/evidence tests when possible;
- latency problem -> per-stage latency.

No recorded metric means no verified improvement.

## 14. Configuration and Testing Rules

### Configuration

Tunable engineering/research choices belong in configuration when practical.

Examples:

- candidate counts;
- top-k;
- rerank depth;
- modality weights;
- thresholds;
- token/image budgets;
- temporal windows;
- timeouts/retries;
- model checkpoints;
- artifact versions.

Do not hide important experiment choices as magic constants in business logic.

A default value is not a scientific truth.

### Testing

Test changes at the layer they affect.

**Schema/contract changes**
- validation;
- serialization;
- important invariants;
- required backward compatibility.

**Data/enrichment**
- canonical identity preservation;
- deterministic behavior where expected;
- partial failure/resume;
- lineage/versioning.

**Retrieval**
- ranking behavior;
- filters;
- modality fallback;
- canonical identity preservation;
- small hand-checkable fixtures.

**Temporal logic**
- use synthetic examples whose correct result can be reasoned about manually.

**VQA**
- separate localization failure from reasoning failure when possible.

**TRAKE**
- do not casually break a working alignment path while modifying shared code.

## 15. Agent Workflow

Before a non-trivial change:

1. Read this `AGENTS.md`.
2. Inspect the active public entry point.
3. Trace the real runtime call path.
4. Inspect relevant schemas/contracts.
5. Inspect nearby tests.
6. Inspect relevant config.
7. Search for existing types/functions before creating new abstractions.
8. Check `KNOWLEDGE.md` for prior research/decisions.
9. Research relevant literature for algorithmic/non-trivial decisions.
10. Save material findings to `KNOWLEDGE.md`.
11. Separate SOURCE/PAPER facts from PROPOSED ideas.
12. Discuss architecture-changing or paper-worthy ideas with the user.
13. Implement the smallest clear solution.
14. Add/update tests.
15. Run focused validation before broad repository tests.
16. Report what changed, what was tested, and what remains uncertain.

Do not start by writing code before understanding the actual call path.

## 16. Source-of-Truth Priority

When information conflicts, use this precedence:

1. user's latest explicit instruction;
2. latest official competition specification/scorer/organizer notice;
3. active repository code, tests, config, and artifact formats;
4. approved architecture/spec documentation;
5. this `AGENTS.md`;
6. current implementation plans;
7. `KNOWLEDGE.md` research notes;
8. papers/external implementations;
9. engineering hypothesis.

A paper does not override a competition rule or repository invariant.

A stale plan does not override working code that has already completed a migration.

Never silently revert unrelated teammate work merely to match an old document.

## 17. Do / Don't

### Do

- understand the task semantics before optimizing;
- preserve `video_id`, `frame_id`, `frame_idx`, and timestamp mappings;
- keep code simple and easy to debug;
- write meaningful module/class/function docstrings;
- comment important **why**, not obvious **what**;
- use whitespace to separate logical stages;
- reuse before creating abstractions;
- preserve specialist evidence/provenance;
- use scholarly research tools for meaningful algorithmic decisions;
- save material research to `KNOWLEDGE.md`;
- distinguish SOURCE, PAPER, PROPOSED, VERIFIED, and REJECTED claims;
- discuss potentially publishable ideas with the user;
- use reproducible experiments and ablations;
- measure the stage that is actually failing;
- keep expensive offline work out of request paths;
- keep tunable choices explicit in config;
- keep tests small and hand-checkable where possible.

### Don't

- do not turn this hackathon repository into an enterprise framework;
- do not introduce speculative abstractions for hypothetical future use;
- do not create duplicate schemas with slightly different names;
- do not hide scientific/engineering choices in magic constants;
- do not destroy canonical frame identity;
- do not confuse `frame_idx` with keyframe order;
- do not flatten specialist evidence and discard the originals;
- do not treat unevaluated evidence as automatically negative;
- do not let model outputs invent canonical IDs;
- do not run expensive VLM reasoning over the full corpus;
- do not rebuild large offline artifacts during serving;
- do not claim improvements without measurements;
- do not copy a paper blindly without testing HCMAI relevance;
- do not silently implement potentially paper-worthy ideas;
- do not over-comment trivial code;
- do not write dense, clever code that is harder to debug than a straightforward version;
- do not rewrite stable task-specific logic unless the requested change requires it.

## 18. What an Agent Should Report After a Substantial Change

Report concisely:

- files inspected;
- files changed;
- behavior before/after;
- important design decisions;
- research consulted when applicable;
- whether `KNOWLEDGE.md` was updated;
- tests and results;
- metrics/benchmarks when applicable;
- compatibility impact;
- known limitations;
- assumptions requiring validation;
- research/paper opportunities discovered.

## 19. Final Principles

1. **Keep the system competition-correct.**
2. **Prefer simple, readable, debuggable code over production-style complexity.**
3. **Preserve canonical identity from ingestion to submission.**
4. **Preserve specialist evidence and provenance.**
5. **Retrieve/localize evidence before expensive reasoning.**
6. **Research meaningful algorithmic decisions before committing to them.**
7. **Record useful research knowledge in `KNOWLEDGE.md`.**
8. **Treat papers as evidence for hypotheses, not proof for HCMAI.**
9. **Use experiments and ablations to validate optimization ideas.**
10. **Surface potentially publishable ideas instead of silently burying them in code.**
11. **Reuse before creating abstractions.**
12. **Write code that another teammate can understand and debug quickly.**

The goal is not to build the most abstract or production-like architecture.

The goal is to build the **smallest, clear, testable, research-informed system that reliably retrieves the right evidence and produces the correct competition output**.
